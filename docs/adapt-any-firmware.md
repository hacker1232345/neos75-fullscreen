# 别人家的固件：自动适配

同款键盘（AULA Neos75 V2.0）出厂刷的固件版本各不相同。以前每来一份新固件，都要人工
用反汇编找出补丁点的新偏移、重新做一份 profile，一个人一天顶多弄两三份。这套工具
把这件事变成「拖一个文件进去，等两分钟」。

## 一句话原理

不再记「补丁打在 0x2c53c 这一格」，改成记「补丁打在**这段字节**所在的那一格」。

补丁点前后那段字节（锚点）在官方固件里是**全片唯一**的，换一份固件、整个代码区往后
挪了 1 KB，那段字节还是那一段字节 —— 搜一下就知道新位置。搜到位置以后再核对一遍
「这儿的旧字节到底是不是我要改的那个」，对不上就拒绝写入，绝不硬改。

## 两条铁律（这两条是踩坑换来的）

**① 锚点必须从「这一层的源镜像」预先算好并落盘，不能现算。**

第一版是「在新固件上，从旧偏移取上下文当指纹」。布局一迁移，取到的就是**错位**的
字节；那段错位字节本身也恰好唯一，于是算出「位移 0」—— 看起来成功，实际把补丁写到
完全不相关的位置上。自检第一轮就被这个骗过去了。

**② 注入层的代码不能按字节搬，必须按符号重新汇编。**

覆盖组件那 1960 字节不是「改几个字节」，是往一片全 0xFF 的空闲带里塞一段新代码，
里面含 `bl 0x2637c`（调用厂商的分配函数）这类**绝对地址**。厂商函数在新固件里会跟着
挪，硬搬过去就是调用不相干的地址，屏幕直接跑飞。所以注入层走另一条路：用 16 字节的
入口签名把 11 个厂商函数在新固件里重新找出来，把模板里的符号全换成新值，重新汇编。

附带一个结论：RAM 变量（页表指针、上下文块、毫秒计数器）**不需要签名**。它们是固定
的 `.bss` 地址，跨固件基本不变。实测在 clean 镜像里搜这些地址的 `movw` 引用是 0 处
—— 因为那些引用只存在于注入代码里，而 clean 镜像里根本没有这段代码。

## 用户视角：三步

1. 在程序里点「备份」，得到一个 `491520` 或 `491536` 字节的 `.bin`。
2. 开一条 issue，把文件拖进去，打上 `firmware-adapt` 标签。
3. 等机器人回帖。帖子里有：这份固件能套哪几层、一份打好补丁和 DFU 校验的完整镜像、
   一份派生 profile（别人拿同样的固件就不用再算）。

机器人**永远不碰设备**：不用 USB、不刷写，只在内存里算字节。刷不刷、什么时候刷，
由用户自己在本地决定。

## 命令行视角

```sh
# 只看结论（人话）
python tools/adapt_firmware.py --firmware backup.bin

# 完整报告
python tools/adapt_firmware.py --firmware backup.bin --json

# 直接产出可刷镜像（含 16 字节 DFU 后缀与 CRC）
python tools/adapt_firmware.py --firmware backup.bin --build out/adapted.bin

# 把派生 profile 写到目录，给下一次同样的固件用
python tools/adapt_firmware.py --firmware backup.bin --emit out/profiles/

# 三级自检（不接设备）
python tools/adapt_firmware.py --selftest
```

`--build` 的退出码是有含义的：`0` 产出成功、`3` 补丁点对不上（布局差异太大，
需要人看）、`4` 这份固件已经是最新状态（没有要打的层）。

## 修不掉的三种情况

| 情形 | 报告里怎么写 | 为什么 |
| --- | --- | --- |
| 锚点在新固件里搜不到 | `unlocatable` | 那段字节被改过，或整块被重排 |
| 搜到了、但旧字节不是预期 | `mismatch` | 代码改过，硬改会坏 |
| 厂商函数签名找不到 | `injection` + `unresolved` | 代码被改过，不敢重新汇编 |

第三种最关键：**签名找不到就说明厂商改了函数体**，这时候任何自动重新汇编都是猜的，
一律放弃。宁可报「这份固件需要人看」，也不出一份可能变砖的镜像。

## 目前验证到什么程度

离线全绿，真机只验过一部分：

- `tools/symbols.py --selftest`：两份已知镜像各 **13/13** 解析成功，地址与参考一致。
- `tools/adapt_firmware.py --selftest`：**8 项**通过 —— 原位识别、+0x20 迁移后按锚点
  全部搬移、垃圾镜像拒绝、整链逐层串接每层代码指纹与声明一致。
- 三份「在 `0x9000` 插 0x400 字节 FF」的模拟迁移镜像（原版 / 全屏 / clean 三种起手），
  `reference 20/20`、`clean 5/5`、`widget 3/3` 全部 ready。
- 两条独立路线（直接 `build_widget.patch` vs 走适配器的 `apply_entries`）在三份迁移
  镜像 × 两种页掩码下的产物**逐字节相同**。
- 设备当前的 `ov6p`（覆盖组件全开）能被正确识别成「只差页掩码」，产出与官方
  `widget-none` 镜像的代码指纹**完全一致**（`ec412e092dc8…`）。

**没验证的**：真机刷写。所有断言都在字节层面，没有一份产物经过实机启动。
这一条写在风险清单第一行。

## 后续风险清单

| 风险点 | 触发条件 | 后果 | 前兆 | 对策 |
| --- | --- | --- | --- | --- |
| 产物没经过实机启动 | 用户直接刷 `--build` 的输出 | 屏幕不亮 | 无前兆，只能靠刷前备份 | 刷前强制备份；`docs/找BOOT0指引_20261102.md` 的 SWD 通道兜底 |
| 锚点在真机上不唯一 | 同款固件里出现重复的厂商代码片段 | 定位到错位置、写坏 | 报告里 `unlocatable`+多次命中 | 锚点生成时要求源/目标两边都唯一；命中>1 直接拒绝 |
| 符号签名被厂商改掉 | 新版固件重写了那几个函数体 | 注入层放弃（此时仍能套前两层） | 报告里 `unresolved` + 列出缺了哪个函数 | 只跳过注入层，前两层照打；不假装成功 |
| 空闲带不够大 | 新固件把 0x4aacc 之后的空间用掉了 | 注入层放不下 | 报告里 `no-room` + 给出实测剩余长度 | 按实际最大 FF 区重新定位；不足就报错退出 |
| `key` 与 `mask` 语义冲突 | 用户同时要「全开」又选了「关闭」 | 掩码被最后一次写入覆盖 | 界面显示与实际不符 | 掩码是单值，后写覆盖前写；UI 只允许一个来源 |
| issue 里贴的不是备份 | 用户传了截图、ZIP、屏幕固件 | 适配器读错东西 | 长度不是 491520/491536 | `check()` 先判长度与空白比例，不合格直接回帖说明 |
| 附件被 GitHub 转存后失效 | user-attachments 链接过期 | 机器人抓不到文件 | 下载 404 | 回帖里说明「请重新拖一次文件」；产物留在 issue 里不依赖原链接 |
| 派生 profile 被误当正式 profile | 用户把 `auto-*.patch.json` 拷进 `firmware/profiles/` | 强制模式对派生层做「逐条核对原始旧字节」，必然失败 | `forceBlind=true` 且 changed 很小 | 派生 profile 的 before 是「迁移镜像上的字节」，只该给 `build_adapted()` 用 |
| 适配器在 CI 上跑超时 | 一次 issue 触发多次重跑 | 回帖延迟 | job 超过 5 分钟 | workflow 用 `concurrency: cancel-in-progress` |
| macOS 上文件名大小写 | 用户备份叫 `Backup.BIN` | 正则匹配不到 | 回帖说「没找到附件」 | `URL_RE` 同时匹配 `.bin` 与 `.BIN` |
